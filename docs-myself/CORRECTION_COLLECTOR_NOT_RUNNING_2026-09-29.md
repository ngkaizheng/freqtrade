## 1. 三个静默失败，一个套一个

| # | 症状 | 根因 | 为什么静默 |
|---|---|---|---|
| **1** | 从未创建数据库文件 | 配置键写成了 **`database_url`**，正确键是 **`db_url`**（`configuration.py:153`、`constants.py:23`） | **freqtrade 不拒绝未知配置键**，静默回退到默认 `sqlite:///tradesv3.dryrun.sqlite`（仓库根目录） |
| **2** | 「2 个未平仓交易，请手动处理」而无法启动 | 因为第 1 条，它打开了仓库根目录那个**旧库**，里面是早先会话的模拟持仓 | **这条警告读起来像市场状况，不像配置拼写错误** |
| **3** | 进程活着、每 60 秒打一次心跳，但状态是 **STOPPED** | 配置缺 **`initial_state: "running"`**，它在等一个**没人会发的 `/start` RPC** | **没有报错、没有警告，而心跳看起来和一个健康运行的 bot 一模一样** |

## 2. 这一轮真正的收获

> **「它能启动」不等于「它在运行」。**
> **而**「它有心跳」**更**不等于它在运行。

第 3 条是最阴的：一个 **STOPPED 状态的 bot 每分钟打一次心跳**，
从进程列表、CPU、内存、数据库文件、启动日志看**全部正常**。
**如果我只是「再启动一次然后看一眼日志有没有报错」，我会再次报告它在运行。**

所以我写了 `tools/perp_short/verify_collector.py`，它检查三件
**「能启动」的冒烟测试永远不会检查**的事：

1. **数据库文件存在且非空**
2. **日志里出现过 `Changing state to: RUNNING`，且最后一次状态变更是 RUNNING 而不是 STOPPED**
3. **最后一次心跳携带的状态字段是 `RUNNING`**——而不是「有心跳」

**当前结果（本次真正修好之后）：**

```
[1/3] database  : OK  forward_perp.dryrun.sqlite (94,208 bytes)
[2/3] state      : RUNNING x1
[3/3] last heartbeat STATE = RUNNING
VERDICT: the collector is RUNNING
```

## 3. 为什么这条比前面那些 bug 更值得记

本项目记录的 11 个静默 bug **每一个都产出了一个自信的错数字**——
所以它们原则上**是可能被抓到的**，只要有人拿另一个工具去对一遍。

**这一个什么都不产出。** 它产出的是一个「看起来一切正常」的长驻进程。
**它的证据形式恰恰是「没有报错」。**

> **对任何长期运行的东西——采集器、监控、服务——
> 「没有报错」和「有心跳」都不是它在工作的证据。
> 必须有一条它自己产出的、只有在真的做事时才会出现的东西。**
>
> 对这个收集器，那条证据是：**一笔成交被写进数据库，并且带上了分析需要的字段。**
> **在攒够第一笔之前，「它在运行」这句话本身就是未经验证的。**

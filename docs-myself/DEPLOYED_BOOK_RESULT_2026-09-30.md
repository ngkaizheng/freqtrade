## 0. 这一轮做了什么

之前的 `HOW_TO_RUN` §4 挂着一张表，但**那张表不是部署版的数字**——它是 N=50、
1% 风险下的结果，而且产生它的工具**自己会重新计算仓位**。
用户问「这个到底能赚多少」，应该得到一个**只用页面上那三个设置**跑出来的数字。

所以本轮：用**部署配置本身**（未做任何修改）跑了一次完整回测，
然后用一个**先证明自己能复现引擎**的工具把它重定价到实测成本档。

## 1. 引擎自己的输出

```
config            : user_data/config_perp_forward_dry.json  （一字未改）
strategy          : PerpShort4hDeploy
universe          : 40 symbols, liquidity-ordered
risk_per_trade    : 0.005      atr_stop: 4.0
window            : 2023-03-22 -> 2026-08-31
trades            : 1,111 (all short)      starting 10,000 USDT
trades            : 1,111
total             : +113.74%   (10,000 -> 21,373.78)
CAGR 24.44%  Sharpe 2.06  Sortino 4.93  Calmar 12.10
PF 1.36   maxDD 14.16%   winrate 52.84%
```

**⚠ 一个值得注意的差别：1% 风险的同一白名单版本只产生 777 笔交易，0.5% 产生 1,111 笔。**
机制是仓位变大后 `max_open_trades=24` 更快占满，后续入场被挡掉。
**所以「降低单笔风险」在这个策略上同时也提高了交易频率**——这在别处可能是优点，
但它意味着 1% 和 0.5% 的收益**不是简单的线性缩放**，任何缩放假设都是错的。

## 2. ⚠⚠ `cost_frontier.py` 坏了：它不是重定价，是重跑另一个策略

拿它跑同一份档案：

| | 引擎 | `cost_frontier` |
|---|---:|---:|
| 总收益（引擎自己的成本） | **+113.74%** | **+3687%**（毛） |
| 最大回撤 | 14.16% | 62–67% |

**32 倍的差距不是舍入误差。** 原因在结构上，不是一个笔误：

`cost_frontier.replay` **完全忽略引擎导出的 `amount`**，而是自己重算仓位：

```python
notional = risk_per_trade * equity / (ATR_STOP * (atr / entry))
stake    = min(notional / lev, equity * max_stake_frac)
```

而它用的是**自己的默认值**：`ATR_STOP=1.5`（`cost_frontier.py:61`）和
从 `user_data/config_perp_short.json` 读来的 `risk=0.01`（第 269 行）——
**部署的书跑的是 `atr_stop=4.0` 和 `risk=0.005`。**

```
重定价工具的仓位  = 0.01 / (1.5 * atr)  -> 约 25% 的权益（还被 25% 上限截住）
部署版的仓位      = 0.005 / (4.0 * atr) -> 约  4.9% 的权益
                  = 5.3 倍
```

**于是同样的 bps 成本，它要扣掉 5.3 倍。**

**后果，必须说清楚：**

> **本项目此前所有「实测成本」下的收益数字，成本扣减都被夸大了约 5 倍，收益被严重低估。**
> 引擎自己打印的数字**一直是正确的**——错的只是之后施加在它们身上的成本调整。

这解释了新旧两个数字为什么差那么多（见 §3）。

## 3. 新的权威表（部署配置，实测成本）

**先验证工具，再看任何数**：

| | 总收益 | 最大回撤 |
|---|---:|---:|
| 引擎打印 | **+113.74%** | 14.16%（逐 bar 盯市） |
| 重定价工具（引擎自己的成本） | **+113.74%** | 18.43%（按平仓记账） |
| **差** | **0.00 个百分点** | 4.27 pp（**不是同一个统计量**） |

> **⚠ 两个回撤不可直接比较。** 引擎的是**逐 bar 盯市**曲线（含未平仓头寸）；
> 这个工具**只在平仓时记账**，所以它是「平仓口径」。
> 它列出来是为了让各成本档之间可比（每行口径相同），**不是对引擎回撤的第二个意见**。
> 混着比就是 LESSON L3：**一次比较两处不同**。

**验证通过（0.00 pp）之后，才允许报出成本档：**

## 4. 新旧对比：错在哪里，纠正了多少

| | 旧表（`cost_frontier`，N=50/1%风险） | 新表（`cost_reprice`，N=40/0.5%风险） |
|---|---:|---:|
| COVID 档总收益 | +89.9% | **+90.3%** |
| CAGR | 20.5% | **20.7%** |
| Sharpe | 0.67 | **2.10** |
| PF | 1.17 | **1.28** |
| 为正年数 | 3/4 | **4/4** |

**总收益和 CAGR 几乎一样，Sharpe 差了 3 倍。** 这说明旧的 Sharpe 0.67
**不是仓位大小造成的**（Sharpe 对仓位缩放不变），
**而是旧的成本扣减把收益曲线压成了一个形状更平的序列**。
**这正是「一个错误的工具，产出一个看起来很正常的结果」的样子。**

## 5. 这一轮记下的坑

19. **一个算出来但没人用的变量，是静默的空操作。** `cost_reprice` 第一版把各成本档的
   成本算进了一个叫 `cost` 的变量，然后**用的是另一个参数**——
   于是**每一行成本档都打印出引擎自己的数字，整条成本曲线是平的**。
   表看起来完全正常（单调、格式整齐）。
   **识别它的信号是：成本列在变，其它列全不变——真实的成本不会这样。**
   和 #6（风控失败时放行）、#11（翻页循环不前进）是同一族。
20. **⚠「重定价」如果重算了仓位，就不是重定价，是重跑另一个策略。**
   本项目的成本重定价工具一直是这样，而且没人发现，
   因为**它输出的表形状完全正常**。
   **一个成本工具必须先证明自己能在引擎自己的成本下复现引擎，否则不许出数。**
21. **一个目录存在 ≠ 这个目录能读你要的数据。** `user_data/data/wide_ft` **存在**（96 个文件），
   但里面没有 `1000BONK_USDT_USDT-4h-futures`——而 `cost_frontier.py` 就是读不到这个文件。
   **第一版 `tool_paths_gate.py` 只查目录是否存在，因此给了一个假的 PASS**，
   和 #13 是同一个错：那条门槛不可能被违反。改成「能不能读部署配置的那 40 个币」之后才有用。
22. **数据面板换了名字，工具不会跟着换。** 19 个文件仍然指向 `wide_ft`，
   其中 `cost_frontier.py` 和 `r_stats.py` 在**现行工具链**里，两个都坏了。
   **第三次同族事件**（`verify_stop.py` 第一次，本轮发现另外两个）。
   `tool_paths_gate.py` 是为这一族建的闸门。

## 6. 现在的状态

`cost_frontier.py` **停用**，不要再用它出任何对外数字。
`cost_reprice.py` 取代它，并且**带一个不能绕过的验证闸门**。
`HOW_TO_RUN` §4 已经换成部署版的权威表，并保留了旧表和更正记录，
以便看出是什么被什么推翻了。
